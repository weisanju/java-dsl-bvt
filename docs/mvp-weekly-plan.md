# Java + Karate 接口测试平台 MVP（单人版按周排期）

## 1. 规划目标

- 面向单人维护仓库，在 6 周内交付可运行 MVP。
- 主链路跑通：`用例管理 -> 套件编排 -> 触发执行 -> 查看报告`。
- 先做后端 API 和执行能力，前端页面后置。

## 2. 单人约束与策略

### 约束
- 只有 1 位开发者，时间与上下文切换成本高。
- 不能同时维护太多基础设施组件。

### 策略
- 采用单体架构（Spring Boot），不拆微服务。
- P0 先用最小可行方案：先手动触发执行，再加定时与 CI。
- 只保留必要模块，复杂治理能力后置。

## 3. MVP 范围（P0）

1. 项目/环境/变量管理（支持 JSON/YAML 数据驱动）。
2. 用例管理（Karate 脚本保存与版本号）。
3. 套件管理（用例顺序编排）。
4. 手动触发执行，记录 run/task/result 状态。
5. 报告查询（通过率、失败详情、耗时）。
6. 基础健康检查与日志。

## 4. 非目标（本期不做）

- 多租户、审批流、复杂 RBAC。
- 分布式多 Runner 与复杂调度策略。
- gRPC/WebSocket/性能压测能力。

## 5. 按周排期（6 周）

## Week 1：工程与数据基线

### 功能目标
- 初始化 Spring Boot 工程、数据库连接、基础分层。
- 建立 DDL（直接使用 `docs/platform-mvp-ddl.sql` 中核心表）。

### 实现动作
- 搭建包结构：controller/service/repository/domain。
- 接入 Flyway（可选）管理 DDL。
- 建立健康检查与统一异常处理。

### 验收标准
- 服务可启动，数据库初始化通过。
- `/actuator/health` 正常返回 UP。

---

## Week 2：用例与数据集管理

### 功能目标
- 用例 CRUD（Karate 脚本）。
- 数据集 CRUD（JSON/YAML）。

### 实现动作
- 实现 `t_test_case`、`t_test_case_data_set` 的 API。
- 保存前做 JSON/YAML 语法校验。
- 用例更新自动递增 `version_no`。

### 验收标准
- 可创建并更新 case。
- 可绑定并读取 JSON/YAML 数据集。

---

## Week 3：套件编排与执行上下文

### 功能目标
- 套件 CRUD、套件与用例绑定。
- 构建执行上下文（环境 + 变量 + 数据集）。

### 实现动作
- 实现 `t_test_suite`、`t_test_suite_case` API。
- 完成变量覆盖逻辑（全局 < 环境）。
- 提供执行前预览接口（查看渲染后的参数）。

### 验收标准
- 一个套件可按顺序绑定多个用例。
- 执行前可确认最终变量值。

---

## Week 4：Karate 执行链路打通

### 功能目标
- 手动触发一次完整执行并落库结果。

### 实现动作
- 实现 `POST /api/suites/{id}/run`。
- 写入 `t_test_run`、`t_test_run_task`、`t_test_case_result`。
- 对接 Karate Runner，解析执行结果。

### 验收标准
- 单次触发后，run 状态能从 QUEUED 变为 SUCCESS/FAILED。
- 失败 case 可查看断言失败信息。

---

## Week 5：报告与可观测

### 功能目标
- 提供报告接口和基础趋势统计。

### 实现动作
- 实现 `/api/runs/{id}/report`（明细）。
- 实现 `/api/reports/trend`（近 7 天成功率）。
- 对敏感字段（token/password）做日志脱敏。

### 验收标准
- 报告可查看通过率、失败原因、耗时。
- 趋势接口可返回按天聚合结果。

---

## Week 6：自动化触发与稳定性

### 功能目标
- 增加定时触发（P1 轻量版）与重试能力。

### 实现动作
- 实现 `t_test_plan` 基础字段及 API。
- Spring Scheduling 按 cron 触发执行。
- 网络类异常支持 1~2 次重试（断言失败不重试）。

### 验收标准
- 定时计划可按 cron 自动执行。
- 失败重试后状态与日志可追踪。

## 6. 功能清单与实现思路（汇总）

| 优先级 | 功能 | 实现思路 | 交付定义 |
|---|---|---|---|
| P0 | 用例管理 | DB 存脚本 + 版本控制 | Case CRUD 完整可用 |
| P0 | 数据集管理 | JSON/YAML 文本存储 + 校验 | DataSet CRUD + 校验错误提示 |
| P0 | 套件编排 | 套件-用例关系表 + 顺序字段 | 套件执行顺序可控 |
| P0 | 手动执行 | 调用 Karate Runner，结果回填 DB | 可触发并拿到 run 结果 |
| P0 | 报告查询 | 基于 run/result 聚合 | 明细 + 通过率 |
| P1 | 定时任务 | Spring Scheduling + 计划表 | 可自动执行 |
| P1 | CI 触发 | 提供 trigger API + token 鉴权 | CI 可调用 |
| P1 | 重试机制 | 异常分类 + attempt 计数 | 网络抖动场景稳定 |

## 7. 风险与应对（单人版）

1. **功能铺太大，节奏失控**  
   应对：严格按 P0 -> P1 递进，未完成 P0 不进入 P1。

2. **维护成本过高**  
   应对：单体架构优先，少引入中间件。

3. **执行结果难排障**  
   应对：统一 run_id、保留关键请求/响应快照、日志脱敏。

## 8. 完成标准（Definition of Done）

- 能创建用例、绑定数据集、编排套件并手动执行。
- 能查询执行报告并定位失败原因。
- 至少 1 个定时计划可自动执行（P1 轻量目标）。
- 文档与 DDL 与代码保持同步更新。
